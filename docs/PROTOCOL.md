# BLE Protocol Notes

This document summarizes the protocol knowledge that the app relies on. It is an interoperability document, not a claim that every compatible-looking scooter implements every command.

## Evidence labels

- **Confirmed from source**: behavior was traced to the original companion application's client logic.
- **Confirmed by capture/device**: behavior was observed in BLE traffic or device responses.
- **Inferred**: the interpretation fits the available evidence but still needs a live capture or broader hardware testing.

## Transport

The app has observed two candidate GATT layouts used by this scooter family: service/characteristic pairs based on `FEE0/FEE2` and `FFF0/FFF1`. The client tries known layouts in a deterministic order, enables notifications, negotiates MTU, then performs the connection handshake before normal commands are sent.

## Frame shape

Normal application frames use a compact structure containing a protocol marker/state byte, command code, payload length, payload bytes, and a checksum. `ProtocolCodec` is the source of truth for frames generated by this project. A small number of handshake packets are treated as literal protocol constants because the original client sent them that way and they do not all fit the normal checksum rule.

## Implemented command families

| Area | Codes used by this app | Status |
| --- | --- | --- |
| Lock / unlock | 51 | Source-confirmed command direction; status read from telemetry |
| Find scooter | 52 | Implemented start/stop control |
| Startup mode | 53 | Toggle confirmed; exact user-facing semantics can vary by model |
| Cruise control | 54 | Source-confirmed toggle behavior |
| Optional compartments | 55-58 | Experimental/model-dependent; no reliable persistent state field confirmed |
| Performance configuration | 60-63 | Read/write and read-back behavior implemented for supported devices |
| Ambient lighting | 65 | Mode control implemented; only encodings represented safely by the protocol implementation are exposed |
| Headlight | 69 | Source-confirmed toggle behavior |
| Dashboard/work mode | 74 | Model-dependent response behavior |
| Bind acknowledgement | 76 | Used only when the observed status indicates it is appropriate |

## Incoming telemetry

The decoder currently recognizes these families when a scooter reports them:

| Code | Data represented in the app |
| --- | --- |
| 16 | Live motor/battery telemetry such as speed, voltage, battery percentage, and temperature |
| 17 | Status flags, odometer-related state, lock state, gear/unit flags where present |
| 18 | Dashboard/controller hardware and software versions |
| 19 | Throttle and brake sensor values |
| 31 | Battery-management-system information |
| 60-63 | Current configuration/read-back values |
| 74 | Dashboard/work-mode response where supported |

Fields are nullable in `ScooterTelemetry`. A missing field means the app has not received a trustworthy value; the UI should show an unknown state rather than a guessed default.

## Toggle polarity

Several controls in the original client send a value derived from the **current** state, not the desired state. This distinction matters because reversing it can produce an acknowledgement/beep without changing the scooter. The implementation keeps this conversion in `ProtocolCodec` and waits for status telemetry before sending state-dependent toggles.

## Configuration read-back

Codes 60-63 can be queried so the app can display the value actually reported by the scooter after a write. Torque/brake display values are not simple raw bytes; the original client uses command-specific scaling on write and command-specific divisors on read-back. The app mirrors those confirmed conversions rather than applying one shared formula.

## Feature discovery

The original application receives model-specific feature visibility from a remote service. No equivalent complete capability bitmap has been confirmed over BLE. Escooter Control therefore keeps optional features user-configurable and stored locally instead of pretending to auto-detect unsupported hardware.

## Known unknowns

- The semantic purpose of every byte in the post-connect handshake is not known.
- Optional compartment controls appear model-dependent and lack a confirmed persistent state report.
- Some response layouts differ by firmware or model and need more real-device captures.
- A protocol observation on one scooter should not automatically be generalized to every scooter sharing the same BLE naming pattern.

## Contributing protocol findings

A useful protocol contribution includes the scooter/model context, firmware versions if available, the exact action performed, relevant TX/RX frames with personal device identifiers removed, and whether the conclusion came from a source trace, live capture, or inference. Avoid documenting guesses as established behavior.
